# Security audit — October 2026

| | |
|---|---|
| **Scope** | Everything merged to `main` up to and including milestone M1a: the API (`apps/api`), its migrations and database permissions, the web app (`apps/web`), the Docker Compose stack, the nginx configuration, the scripts, and the CI workflows. |
| **Method** | Manual review of every file, with the threat model below. Each finding was reproduced or confirmed in code, fixed, and covered by a regression test where it is testable. Fixes were then checked by **mutation**: removing each fix makes its test fail. The whole stack was also run end to end behind the real nginx configuration in a browser. |
| **Reviewer** | Claude (AI assistant), for the project owner. This is not a substitute for an independent professional assessment before a public or paid launch. |
| **Result** | 13 findings: 0 critical, 0 high, 4 medium, 6 low, 3 informational. All medium and low findings are fixed. |

## Threat model

OpenChart AI stores API keys, portfolios and investment theses for one household or small group, usually on a home server. The audit considered:

- **Someone on the same network or the internet** reaching the web port, including before the owner has finished setup.
- **A malicious website** visited by a signed-in user (CSRF, DNS rebinding).
- **One user of the server** trying to read another user's data.
- **A bug elsewhere in the API** (for example a future SQL injection) and how much damage it could do.
- **Resource exhaustion** on small hardware such as a Raspberry Pi.
- **Leaks into logs, caches and browser history.**

Out of scope: a fully compromised host or Docker daemon, and physical access.

### A1 — Invite tokens written to web-server access logs (Medium)

**Problem.** Invite links looked like `/register?invite=TOKEN`. Opening one is a `GET` request to nginx, which writes the full URL, token included, to its access log. Anyone able to read the logs could redeem an unused invite and join the server.

**Fix.** Links now carry the token in the URL fragment: `/register#invite=TOKEN`. Browsers never send the fragment to a server. The register page reads the token and immediately removes it from the address bar and history. Old `?invite=` links still work.

**Verified by** a web unit test that the created link uses `#invite=`, a test that registration reads the token from the fragment, and an end-to-end run through nginx after which the access log contains no token.

### A2 — App database role could read password hashes (Medium)

**Problem.** The API's database role had `SELECT` on every column of `users`. Row-level security lets owners and admins see every user row, so a single SQL-injection bug anywhere in the API could have exposed every password hash.

**Fix.** Migration `0002` grants `SELECT` only on the profile columns. Sign-in already reads hashes through the narrow `auth_login_lookup` function, so nothing else needed to change.

**Verified by** `test_app_role_cannot_read_password_hashes` (selecting `password_hash` as the app role, even with owner context, is denied).

### A3 — Unbounded memory in the sign-in rate limiter (Medium)

**Problem.** The limiter created a dictionary entry for every (address, email) pair it saw and never removed empty ones, even when only checking. Cycling through made-up emails grew memory forever.

**Fix.** Checking no longer creates entries, expired entries are dropped, and at most 10,000 keys are tracked (the oldest are forgotten first).

**Verified by** three unit tests: expiry, the key cap, and read-only checks.

### B1 — Memory exhaustion through password hashing (Medium)

**Problem.** argon2id uses 64 MiB per hash, by design. Registration hashed the password *before* checking the invite, with no limit, and the thread pool allowed about 40 hashes at once: roughly 2.5 GB of memory from unauthenticated requests. That is enough to crash a Raspberry Pi.

**Fix.** At most two hashes run at the same time across the whole API. Registration with bad invites is rate limited per address *before* any hashing. nginx also limits the sign-in, registration and setup endpoints (see A8).

**Verified by** `test_password_hashing_concurrency_is_capped` (10 parallel hashes never exceed 2) and `test_bad_invites_are_rate_limited_before_hashing` (the 6th bad attempt is refused without hashing).

### A4 — Interactive API docs exposed in production (Low)

**Problem.** `/api/docs` and `/api/openapi.json` were public, describing the entire API to anyone. The docs page also loads scripts from a CDN, which the Content-Security-Policy blocks anyway.

**Fix.** Off by default. Developers can enable them with `OPENCHART_API_DOCS=true`.

**Verified by** tests that both paths return 404 by default and work when enabled.

### A5 — Setup endpoint had no attempt limit (Low)

**Problem.** The generated setup token (144 bits) cannot be guessed, but an owner could configure a short `OPENCHART_SETUP_TOKEN`, and nothing limited attempts.

**Fix.** A configured token must be at least 16 characters, and wrong tokens are rate limited per address (5 per 15 minutes).

**Verified by** a settings validation test and a test that the 6th wrong token gets `429`.

### A6 — Signing in again left the previous session alive (Low)

**Problem.** Signing in from a browser that already had a session created a new one without ending the old one. The old token stayed valid until it expired.

**Fix.** Sign-in, setup and registration end any session whose cookie the browser presents (new `auth_revoke_session` function; holding the token proves ownership).

**Verified by** a test that replays the first cookie after a second sign-in and gets `401`.

### A7 — Session cookie could be planted by a sibling subdomain (Low)

**Problem.** Over HTTPS, a different app on a sibling subdomain could set a cookie with the same name for the parent domain (cookie tossing).

**Fix.** When `OPENCHART_PUBLIC_ORIGIN` is `https://…`, the cookie is named `__Host-oc_session`. Browsers only accept a `__Host-` cookie if it is Secure, host-only and scoped to `/`. Over plain HTTP the name stays `oc_session`. Turning HTTPS on therefore signs everyone out once.

**Verified by** a test of the `Set-Cookie` header under an https origin.

### A8 — Containers ran with more privilege than needed (Low)

**Problem.** The nginx container ran as root, and no container had its filesystem or capabilities restricted.

**Fix.**
- `api`, `migrate` and `web` run with a read-only root filesystem, no Linux capabilities and `no-new-privileges`.
- `web` now uses the unprivileged nginx image (non-root, port 8080 inside the container).
- `postgres` gets `no-new-privileges` (its entrypoint needs root briefly to prepare the data directory).
- nginx rate limits the sign-in, registration and setup endpoints (10 requests a minute per address, burst 10).
- Uvicorn no longer advertises itself in a `Server` header.

**Verified by** the CI Compose smoke test, which now checks the user IDs and read-only filesystems, and a local run of the real nginx config (an 11-request burst passes, then `429`).

### B2 — API responses were cacheable (Low)

**Problem.** Responses containing sessions, audit events and API-key names had no caching instructions, so a browser or shared proxy could store them.

**Fix.** Every `/api/` response carries `Cache-Control: no-store`.

**Verified by** `test_api_responses_are_not_cacheable`.

### A9 — DNS rebinding when no public origin is configured (Informational)

**Problem.** Without `OPENCHART_PUBLIC_ORIGIN`, the CSRF check compares `Origin` with the request's `Host`. A rebinding attack (an attacker's domain pointed at your server) makes these match. The impact is small, because the victim's cookies are not sent to the attacker's domain: only anonymous actions are possible, and those are rate limited or need the setup token.

**Mitigation.** When `OPENCHART_PUBLIC_ORIGIN` is set, requests addressed to any other host are refused. The API logs a warning at startup when it is not set, and the README recommends setting it.

**Verified by** `test_unknown_host_is_rejected_when_public_origin_is_set`.

### B3 — Stale signed-in screen after a remote sign-out (Informational)

**Problem.** If a session was ended from another device, the web app kept showing signed-in pages whose requests all failed.

**Fix.** Any `401` returns the app to the sign-in page.

**Verified by** a web unit test.

### A10 — Known gaps recorded for later milestones (Informational)

These were reviewed and deliberately left for later. Each is on the roadmap:

- **No password reset or owner recovery.** An owner who forgets their password needs database access. A CLI reset command is planned.
- **No master-key rotation.** The `key_version` column is ready for it.
- **No cleanup of expired or revoked sessions.** Harmless, but the table grows; a scheduled cleanup job is on the M10 list.
- **No two-factor authentication yet.** TOTP and passkeys are M1b.
- **No HSTS header.** TLS terminates in front of nginx (Tailscale, Cloudflare Tunnel or a reverse proxy), which should set it.
- **Base images pinned by tag, not digest.** Dependabot tracks them; digest pinning is in M10.
- **The API trusts forwarded client addresses from any peer.** This is safe because its port is only reachable from the `web` container. Never publish the API port directly.

## What held up well

These protections were tested adversarially and needed no changes:

- Row-level security isolates users, including in raw SQL as the app role. Users cannot change their own role.
- The API refuses to start as a superuser, a `BYPASSRLS` role or the schema owner.
- The vault detects tampering with the ciphertext, the wrapped key, the owner, the name or the master key, and plaintext never appears in responses, logs or the audit table.
- The audit log rejects `UPDATE`, `DELETE` and `TRUNCATE`, even from the schema owner.
- CSRF checks block cross-origin, cross-site and same-site writes.
- Login gives the same answer for unknown emails and wrong passwords.
- The setup token is compared in constant time and is needed to claim a fresh server.
- No third-party scripts; strict CSP; secrets never enter image builds.
- GitHub Actions pinned to commit SHAs; dependencies at least 14 days old; dependency audits in CI.

## Addendum — milestone M1b design review (31 October 2026)

Two-factor, passkeys and Google sign-in were reviewed against the same threat model before merging. There are no open findings; the design choices and the tests that hold them in place are recorded here.

| Threat | Mitigation | Covered by |
|---|---|---|
| Password alone signs in to a 2FA account | Login returns `mfa_required` and only a short-lived, single-use flow cookie; the session is created after the second factor | `test_totp_enrolment_and_two_step_sign_in`, mutation check |
| Guessing authenticator codes | 5 wrong codes end the attempt (counted in a separate transaction so rollbacks can't undo it), plus a per-account rate limit | `test_wrong_codes_end_the_sign_in_attempt` |
| Replaying a seen code | Each time step is accepted once, checked in Python *and* in the `UPDATE … WHERE last_used_step < step` (which also stops concurrent use) | `test_a_totp_code_cannot_be_replayed`, mutation check of both guards |
| Leaked database reveals TOTP secrets or recovery codes | Secrets sealed with the vault (master key outside the database); recovery codes stored as HMAC hashes keyed from the master key | code review |
| Passkey phishing, relaying or cloning | WebAuthn origin and RP-ID checks, single-use challenges, user verification required for passwordless, signature counter rollback rejected | `test_bad_assertions_are_rejected`, `test_cloned_authenticator_is_detected`, `test_an_assertion_cannot_be_replayed` |
| Using another user's passkey as a second factor | Assertion must come from a credential owned by the pending user | `test_someone_elses_passkey_is_no_second_factor` |
| Google account takeover or self-registration | Identity must be linked by the signed-in owner, or come with an invite; `email_verified` required | `test_unlinked_google_account_cannot_sign_in`, ID-token tests, mutation check |
| OAuth login CSRF / code injection | PKCE, `state` bound to a browser cookie, `nonce` checked in the ID token, flows single-use | `test_callback_from_another_browser_is_rejected`, mutation check |
| Forged or mis-issued ID tokens | Signature against Google's JWKS, `iss`, `aud`, `exp`, unsigned tokens refused | `test_bad_tokens_are_rejected`, `test_unsigned_token_is_rejected` |
| Stolen session used to weaken the account | Disabling 2FA, managing passkeys, password, Google link and the owner switch need a sign-in within 10 minutes | `test_sensitive_changes_need_a_recent_sign_in` |
| Locking yourself out | Can't remove the last sign-in method, or the last second factor while the server requires one | lockout tests in `test_mfa.py` / `test_google.py` |
| Pre-auth state readable by the app role | `auth_flows` has RLS with no policies and no grants; reachable only through narrow functions | `test_new_tables_are_isolated_and_flows_unreachable` |

Residual notes: Google sign-in could not be exercised against the real Google service in this environment (it needs the owner's OAuth client); it is covered by ID-token verification tests against a local RSA key and full callback flows against a fake Google. The rest was exercised end to end in Chromium, with a virtual WebAuthn authenticator and real TOTP codes, against the real API behind the production nginx configuration.


## Addendum — milestone M2 design review (31 October 2026)

M2 adds the first user content beyond account data, plus an import of untrusted files and a service worker.

| Threat | Control | Evidence |
|---|---|---|
| One user reading or changing another's workspace | Every new per-user table (watchlist, thesis versions, research notes and tasks, positions, alerts, preferences) uses RLS `user_id = app_user_id()` | `test_workspace_is_private_to_each_user` (through the API and with raw SQL as the app role) |
| Rewriting the decision record | Thesis versions are append-only for the app role: `SELECT`, `INSERT`, `DELETE` granted, no `UPDATE`; deleting the history is audited | `test_thesis_history_cannot_be_rewritten` |
| Tampering with the shared instrument catalogue | `instruments` is read-only for the app role; only migrations write it | `test_workspace_is_private_to_each_user` |
| Hostile import files (huge, deeply odd, wrong types, `NaN`/`1e999`, SQL-looking strings) | Server-side parsing with list and version caps, text truncated to column limits, amounts must be finite and positive, symbols mapped only to catalogue IDs, anything else skipped and reported; nginx caps request bodies at 1 MB and the browser refuses larger files before sending | `test_hostile_values_are_ignored_not_trusted`, `test_other_data_is_refused` |
| Duplicates from repeated imports | Merges are idempotent (thesis by timestamp, positions/alerts by value, notes appended once) | `test_importing_twice_adds_nothing` |
| Wildcard abuse in search | `%` and `_` escaped in `ILIKE`; query length and result count capped | `test_instrument_search` |
| Personal data left on a shared computer by the service worker | The worker never handles `/api/`; it caches only the HTML shell and content-hashed static assets | Playwright `opens the app shell offline, but never caches the API`; full-stack cache inspection |
| Precision loss in money values | Amounts are `numeric(28,10)` in Postgres and decimal strings in JSON and the UI; no floats | `test_positions_and_alerts`, formatting unit tests |

Exercised end to end in Chromium against the real API behind the production nginx configuration:
- a prototype's localStorage was imported (6 watchlist items, 2 thesis versions, research, 2 holdings, 1 alert, preferences);
- re-importing the prototype's export file added nothing;
- a second browser signed in and saw the same data;
- the phone layout had no horizontal overflow;
- there were no CSP violations;
- the service worker cache held no `/api/` entries.

One deployment fix came out of this run: nginx served `manifest.webmanifest` as `text/plain`, so it now sets `application/manifest+json` explicitly.

## Addendum — milestone M3 design review (1 November 2026)

M3 adds outbound connections to market-data providers, a long-lived WebSocket, server-wide provider keys and a background task that touches every user's alerts.

| Threat | Control | Evidence |
|---|---|---|
| Another site opening the price WebSocket with the user's cookie (cross-site WebSocket hijacking) | The WebSocket checks `Origin` against the app's own origin (the same rule as CSRF on HTTP), and checks `Host` when a public origin is set, before accepting | `test_socket_rejects_other_origins_and_strangers`; mutation check |
| A stream outliving its session | The session is required to open the socket, and re-checked every minute; signing out, expiry or "sign out everywhere" closes it. Users who must set up two-factor are refused | `test_socket_closes_when_the_session_ends` |
| Resource abuse through the socket | At most 100 instruments per connection and 16 KB per message; invalid ids are dropped; slow clients lose the oldest updates instead of blocking the server | code review |
| Leaking provider keys | Keys are sealed with the vault's envelope encryption under a fixed system identity (AAD binds the provider name), then decrypted only in the server process. API responses carry only a 4-character hint, error messages never include the key, and setting a key needs a recent sign-in and is audited | `test_owner_turns_on_yahoo_and_sets_a_key`, `test_twelvedata_errors_never_echo_the_key`, `test_changing_sources_needs_a_recent_sign_in`; mutation check |
| Members changing or reading server-wide source settings | `data_sources` RLS allows only owners and admins; members get a reduced list from the hub | `test_members_see_which_sources_are_on_but_nothing_else` |
| The background hub needing broad database access | It runs without a user, so RLS gives it nothing. It uses three `SECURITY DEFINER` functions: enabled sources (sealed keys only), instruments with armed alerts (ids only), and triggering crossed alerts (returns owners to notify) | `test_the_alert_function_is_the_only_way_in`, `test_alerts_fire_once_for_their_owner_only` |
| Alerts shown to the wrong user | Fired alerts are delivered only to the owner's open connections | `test_alerts_fire_once_for_their_owner_only`; mutation check |
| Hostile or broken provider responses | Every number is parsed as Decimal and refused if NaN, infinite, negative or absurdly large. Timestamps are range-checked, currencies must match the catalogue (pence and pounds are converted, anything else refused), malformed messages are skipped, and errors become "unavailable", never guessed prices | `test_amounts_refuse_junk`, `test_yahoo_converts_pounds_and_pence_but_refuses_other_currencies`, `test_coinbase_stream_skips_bad_ticks` |
| Terms-of-use exposure for unofficial data | Yahoo is off until the owner accepts its terms, and the acceptance is recorded with who and when | `test_owner_turns_on_yahoo_and_sets_a_key` |

Residual notes:
- `market_trigger_alerts(instrument, price)` can be called by the app database role with any price. Only the API process holds that role, and no HTTP route reaches it, so this is accepted.
- Adapters are now tested against responses recorded from Coinbase, Kraken and Yahoo. Live verification on 1 November 2026 found two issues, both fixed:
  - Yahoo's weekend previous close produced a false 0% change.
  - Lightweight Charts' attribution logo injected an inline `<style>`, which the CSP rightly blocked. The logo was replaced with a plain link, and browser tests now run under the production CSP so this class of problem is caught.
- Twelve Data has not yet been exercised with a real key.
- The WebSocket was exercised end to end through the production nginx configuration (upgrade headers, 1-hour timeouts) in Chromium.

## Addendum — milestone M3½ design review (1 November 2026)

The desktop app runs the database and API on the user's own computer, and adds a native window, a keychain and an updater.

| Threat | Control | Evidence |
|---|---|---|
| Other computers reaching the database or API | Postgres listens only on 127.0.0.1, with no Unix socket and SCRAM passwords for every connection, including local ones. The API binds 127.0.0.1. Both ports are random on each start | `initdb` flags and `postgresql.conf` lines in `supervisor/src/lib.rs`; checked `pg_hba.conf` on a real run |
| Other local users or processes using the API | Same sign-in, CSRF, Origin and Host checks as a server. `public_origin` is `http://localhost:PORT`, so requests for any other host (DNS rebinding) are refused | existing auth tests; `test_serve_runs_and_stops_when_stdin_closes` |
| Reading another user's database or keys from disk | The vault key and database passwords are in the OS keychain (Windows Credential Manager, macOS Keychain), never in the data folder. On macOS and Linux the data folder is 0700; Windows profile folders are per-user | `secret_file_round_trip_is_private`; keychain round trip on the Windows and macOS runners |
| Secrets leaking through process environments | Passwords and the master key reach the API only through its environment, which only the same user (or an administrator) can read. Inherited `OPENCHART_*` variables are removed first, so nothing from the user's shell overrides them | code review |
| The page in the window gaining native powers | No Tauri capabilities are defined, so the web app has no IPC (the generated capability list is empty). The prototype is frozen. Navigation is allowed only to the bundled start page and the exact local origin; anything else, and every new-window request, goes to the system browser | `only_the_local_app_and_starting_page_load_in_the_window` |
| Missing nginx protections in desktop mode | The API serves the web app with nginx's exact security headers (CSP and the rest) and nginx's 1 MiB body limit | `test_headers_match_nginx`, `test_large_bodies_are_refused`, `test_no_files_outside_the_folder` |
| The first-run setup token being exposed | It's random on each start, passed only to the API and the window URL fragment (never sent to the server or logged), and removed from the address bar on load. It stops working once the owner exists | `takes the desktop app's setup token from the URL and removes it` |
| A malicious update | Updates are installed only if signed by the project's key, checked against the public key built into the app. The user is asked before installing. Releases are drafts until a maintainer publishes them | Tauri updater; `desktop.yml` |
| Supply chain of bundled binaries | PostgreSQL comes from npm packages pinned to an exact version with lockfile integrity hashes and the 14-day minimum age. Its install script is not run. Crates are pinned exactly with `Cargo.lock`. GitHub Actions are pinned by commit | `package.json`, `pnpm-lock.yaml`, `Cargo.lock` |
| A crash leaving services running | The API exits when the app's end of its stdin pipe closes. A Postgres left running is stopped and restarted cleanly on the next start | crash test on a real run (kill the app, then restart) |

Residual notes:
- The first builds are unsigned, so Windows SmartScreen and macOS Gatekeeper warn on install, and users must override them. Signing and notarisation are planned once certificates exist.
- The Linux PostgreSQL build bundles OpenSSL 1.1. Postgres doesn't use TLS on the loopback connection, and Linux isn't a desktop target yet.
- Once, on Linux (WebKitGTK), the first session after setup wasn't kept and the user had to sign in. It didn't happen again on a fresh install. Watch for it in the hands-on Windows and macOS checks.
